关于SnowLuma在树莓派上hook失败问题解决

发表于2026-08-12|更新于2026-08-12|问题解决
|浏览量:

在docker运行SnowLuma时,登录QQ后的hook过程报错
日志:

问题原因

树莓派内存页大小和一般操作系统不同

内存页(个人理解):虚拟内存 ↔ 物理内存的映射粒度,例如一个20KB的可执行文件需要移到内存中,20KB/4KB=5页….0,20KB/16kb=1页…4(向上取整→2页),一般来说,可以整除4KB的更多,余数也更小,浪费更小,但是比较”零散”,速度慢,16K反之
hook:在程序正常运行中,插入自己想要的代码执行,插入需要知道在内存的哪个位置(地址),内存页错误会导致计算错误

解决方法：切回 4KB 页内核

树莓派官方系统自带 4K 页内核变体（kernel_2712_4k.img），切换即可。

SnowLuma 版本

1.14.4

出问题的适配器

Bridge / Core(协议层)

操作系统

Debian GNU/Linux 13 (trixie) 64-bit，树莓派 5 (BCM2712) 内核 6.18.39+rpt-rpi-2712（默认 16K 内存页，PAGE_SIZE=16384）

部署方式

Docker

Node.js 版本

预构建包

QQ 客户端版本

3.2.31-51102

问题描述

树莓派 5（16K 页内核）上，SnowLuma hook 自动注入 QQ 主进程失败，日志报 “component loading failed: remote mprotect failed for PT_LOAD segment”
切换到 4K 页内核（kernel8.img）后注入成功，怀疑注入器按 4K 页对齐计算PT_LOAD 段地址，与 16K 页内核不兼容

复现步骤

  1. 在树莓派 5（Raspberry Pi OS，PAGE_SIZE=16384）上按文档的 docker run 命令启动容器
  2. 等待容器内 QQ 自动启动
  3. 查看日志：docker logs -f snowluma
  4. 观察到报错：load failed: PID=72 err=component loading failed: remote mprotect failed for PT_LOAD segment

期望行为

hook 自动注入 QQ 主进程成功，扫码登录后进入工作模式，不报 mprotect 错误

实际行为

QQ 正常启动，但 hook 注入失败，日志反复报：
load failed: PID=72 err=component loading failed: remote mprotect failed for PT_LOAD segment

TRACE 日志 / 错误堆栈

补充信息

由于代理出问题,暂无法更新至1.14.5,但我检查 v1.14.5 release notes，本次更新无 hook 注入或内存页相关修复
